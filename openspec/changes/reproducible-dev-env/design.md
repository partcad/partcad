## Context

The repository already has a well-specified development environment: `.devcontainer/devcontainer.json` pins
`ghcr.io/partcad/partcad-devcontainer:0.7.146`, pins its features by digest in `devcontainer-lock.json`, mounts
the Docker socket and cache volumes, sets the `SKIP` list that the hooks depend on, and runs
`pre-commit install --config dev-tools/pre-commit-config.yaml` as its `postStartCommand`. Nothing about that
design is wrong. What is missing is a way to *reach* it without VS Code, and any documentation telling an agent
that reaching it is mandatory.

Two concrete defects surfaced while diagnosing a failing `git commit` on the host:

1. **The git hooks are container-bound.** `.git/hooks/pre-commit` was generated by `pre-commit install` running
   inside the container, so it hardcodes `INSTALL_PYTHON=/home/vscode/miniforge3/bin/python`. That path does not
   exist on the host. The generated script falls through to `command -v pre-commit`, which also fails because
   `pre-commit` is not on the host `PATH`, and the commit aborts with `` `pre-commit` not found ``. The hook
   file is in `.git/`, so it is not version-controlled and cannot be fixed by a repository change — only by
   running the commit in the environment where its assumptions hold.

2. **A hook entry point is missing from the repository.** `dev-tools/pre-commit-config.yaml` declares a `behave`
   hook with `entry: .devcontainer/behave_hook.sh`, but that file is absent. Git history shows it was added in
   `1f97c83` ("feat(devcontainer): add behave hook for parallel testing", #342) and then deleted in `3b6ef57`
   ("feat(partcad-ide-vscode): Publish PartCAD VS Code extension", #281) — a 1-file, 11-line deletion buried in
   an unrelated 200-commit PR that did **not** touch the config referencing it. This is an accidental deletion,
   not a deliberate retirement. It goes unnoticed because `devcontainer.json` sets `SKIP=behave,...`, so the
   hook never executes and never resolves its missing entry point.

The audience for the fix is coding agents, which operate in a terminal and cannot drive the VS Code Dev
Containers extension, and which are explicitly told by the root `AGENTS.md` not to use `--no-verify`.

## Goals / Non-Goals

**Goals:**

- Give coding agents and non-VS-Code contributors a supported, non-interactive way into the same environment the
  Dev Containers extension produces.
- Keep `.devcontainer/devcontainer.json` the single source of truth; add no second place where the image tag,
  `SKIP` list, or hook-install command is declared.
- Restore `.devcontainer/behave_hook.sh` so no hook entry point dangles, and so `SKIP` is a performance/policy
  choice rather than a load-bearing workaround for a missing file.
- Prove the flow end-to-end by using it to commit the staged work with hooks running.
- Write the flow down in `AGENTS.md` and `docs/source/contributing.rst`.

**Non-Goals:**

- Making `git commit` work on the host without a container. The hooks legitimately need the pinned toolchain;
  reproducing it on arbitrary hosts is the problem the container already solves.
- Changing the container image, the image tag, or the contents of `dev-tools/pre-commit-config.yaml`.
- Changing the `SKIP` list. Restoring `behave_hook.sh` makes the config self-consistent; whether `behave` should
  additionally be un-skipped on commit is a separate performance trade-off and is deliberately left alone.
- Adding `@devcontainers/cli` to `pyproject.toml` or `poetry.lock`. It is a Node tool that runs *outside* the
  container to construct it, so it does not belong in the Python dependency set that lives inside it.
- Replacing or deprecating the VS Code Dev Containers workflow.

## Decisions

### Decision 1: Use `@devcontainers/cli` via `npx` rather than a hand-written `docker run` wrapper

`npx --yes @devcontainers/cli up --workspace-folder .` reads `.devcontainer/devcontainer.json` and applies the
image, the digest-pinned features, the mounts, `remoteEnv` (including `SKIP`), `runArgs`, and the
`postCreateCommand`/`postStartCommand` lifecycle — the last of which is what installs the git hooks. Commands
then run inside it via `npx --yes @devcontainers/cli exec --workspace-folder . <command>`.

*Alternative considered: a `docker run` wrapper script.* It would start faster and need no Node, but it would
have to restate the image tag, the mounts, the `SKIP` value, the `--privileged` flag, and the `pre-commit
install` invocation in shell. Those copies would drift from `devcontainer.json` silently, and the drift would
surface as hooks that pass locally and fail in CI — precisely the class of bug this change exists to remove.
Rejected as violating the single-source-of-truth requirement.

*Alternative considered: fixing the host.* Installing `pre-commit` on the host and re-running `pre-commit
install` would regenerate `.git/hooks/pre-commit` with a host Python path. That fixes one machine, not the
repository, and it runs the hooks against host tool versions rather than the pinned ones — which is how a commit
passes locally and fails CI. Rejected.

The cost is a slower first `up` while features install, and a dependency on `npx` and network access on first
use. Node 20 / npm 10 are already present in the documented environment, and the image itself is already pinned
and commonly cached locally.

### Decision 2: Restore `behave_hook.sh` from git history verbatim rather than rewriting it

The original 11-line script is recoverable with `git show 1f97c83:.devcontainer/behave_hook.sh`. It detects core
count, caps workers at 4, and runs `poetry run behavex features --parallel-processes=$WORKERS
--parallel-scheme=feature` — consistent with the hook's own description ("Run Behave tests in parallel using
behavex") and with `behavex = "^4.0.10"` in `pyproject.toml`. Restoring the reviewed original is strictly safer
than inventing a replacement, and it keeps the accidental deletion's reversal auditable.

*Alternative considered: deleting the `behave` hook entry from the config instead.* That would also make the
config self-consistent, but it discards the intent of #342 on the basis of a deletion that the history shows was
unintentional. Rejected.

Note the restored script's own behavior is not validated by this change, because `SKIP=behave` keeps it from
running on commit. What is validated is that the entry point resolves — which is what the spec requires and what
would break the moment anyone adjusts `SKIP`.

### Decision 3: Document the host/container boundary explicitly in `AGENTS.md`

The current root `AGENTS.md` lists `poetry install`, `pytest`, and `behave` with no statement of where they run,
which reads as host instructions and is how an agent ends up committing on the host. The revision states, for
every command, whether it runs on the host or inside the environment, and names `` `pre-commit` not found `` as
the diagnostic signature of being outside it. This matters more than the command list itself: an agent that
misreads the boundary reaches for `--no-verify`, which is the failure mode the existing instructions already try
to forbid without explaining how to comply.

### Decision 4: Validate by committing the real staged change, not a scratch commit

There are 70 staged files (the OpenSpec/agent tooling work). Using them as the validation subject exercises the
hooks against a realistic diff — trailing whitespace, end-of-file, YAML, JSON-schema, shellcheck, and hadolint
checks all have material to act on — rather than against an empty or synthetic change that would prove little.

## Risks / Trade-offs

- **First `devcontainer up` is slow (features install, image pull if uncached).** → The image tag is already
  cached locally, and features resolve from the committed digest lock. Document the expected one-time cost so it
  is not mistaken for a hang.
- **`npx` requires network access on first use.** → Once fetched, `@devcontainers/cli` is cached by npm. If the
  environment is fully offline, the VS Code path and a manual `docker exec` into an already-running container
  both remain available; neither is being removed.
- **File ownership mismatch between host and container users.** → The image's `vscode` user and the host user
  are both uid 1000 here, so bind-mounted files keep consistent ownership. Worth verifying during
  implementation, since a mismatch would make files appear root-owned and break the commit.
- **Git identity and commit signing may not be configured inside the container.** → `git config user.name/email`
  come from the bind-mounted repo's `.git/config` when set locally; if identity resolves from a host-global
  `~/.gitconfig` that is not mounted, the commit fails. Must be checked during validation, and documented if it
  needs handling.
- **The restored `behave_hook.sh` remains unexercised while `SKIP=behave` stands.** → Accepted, and stated
  plainly in the spec: the requirement is that entry points resolve, not that every hook runs on every commit.
- **Documentation drifts from `devcontainer.json` over time.** → Mitigated by the specs forbidding docs from
  restating environment values as authoritative; docs name the file as the source instead.

## Migration Plan

No migration is required — nothing existing changes behavior. The dev container definition, the pinned image,
and the hook configuration are untouched. Contributors on the VS Code workflow are unaffected; contributors and
agents on the terminal gain a path that did not previously exist. Rollback is deleting the added documentation
sections and `behave_hook.sh`, which returns the repository to its current state.

## Open Questions

- Should `behave` eventually be removed from the `SKIP` list now that its hook script exists again? This change
  deliberately does not decide that; it is a commit-latency trade-off worth its own discussion, and the existing
  `SKIP` entry predates the script's restoration.
- Should CI assert that every repository-relative `entry` in `dev-tools/pre-commit-config.yaml` resolves to an
  existing executable file? That would have caught the #281 deletion at review time. Out of scope here, but it
  is the durable fix for the class of defect rather than the instance.
