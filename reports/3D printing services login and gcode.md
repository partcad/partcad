# Ship Craftcloud first, scoped keys next, cookies never

PartCAD's first `manufacturer` provider should be **Craftcloud**. It quotes and orders with no credential at all, accepts STEP, publishes its live material catalogue, and sends payment to a hosted checkout page. It needs nothing from `pc login` and nothing PartCAD cannot already send. **3DAPI** should come second, ahead of Slant 3D. It is the only candidate whose self-serve key can be limited to quoting, so a leaked key cannot spend money. It also takes STEP today, its checkout link can return to PartCAD's loopback listener, and it alone hands back the exact 3MF file it will print. **Slant 3D** drops to third. Its key is self-serve but unscoped and charges the card on file, it takes STL only, it has shipped provably only in the US, and the mock server the earlier plan relied on imitates a retired v1 API. **Materialise OnSite** remains the option for business buyers. **Shapeways** is one test order away from "build". The new entrant **X3D Studios** is the only service found that prints a customer's Bambu `.gcode.3mf` "exactly as exported". Any plugin that would replay a user's web-session cookie against Xometry, Protolabs, Fictiv or their peers should be refused from the public index outright. Two PartCAD facts shape all of this. `pc login` stores an API key and a session cookie in exactly the same way: in plaintext in `~/.partcad/config.yaml`, sent to the daemon with every command, with no way to write a refreshed token back. And `pc config` prints every saved plugin credential verbatim today, a confirmed leak that must be fixed before any credentialed provider ships. On G-code, no bureau takes it. The shortest path to "the print you validated" is the user's own printer through OctoPrint, Moonraker or PrusaLink. PartCAD's existing filament (FFF) route can reach those once it gains a printer start/end profile and a sender on the client. Reaching a paid service with the file unchanged requires a Bambu-dialect `.gcode.3mf`, most cheaply produced by an unmodified OrcaSlicer run as a route `implementation:`.

## Craftcloud stays first, and 3DAPI overtakes Slant 3D for second

Three tests decide the order. First, can PartCAD quote with what it sends today? Its manufacturer loader renders STEP and nothing else, and logs an error for any provider whose `caps` lacks `step` ([plugin_factory_provider_manufacturer.py:112-131](../src/partcad/plugin_factory_provider_manufacturer.py#L112)). Second, can each user obtain their own credential without a human gate? Third, does that credential limit the damage if it leaks, and does ordering keep card data out of PartCAD? Ordering itself is unimplemented: `ProviderRequestOrder.__init__` raises `NotImplementedError` ([plugin_request_provider_order.py](../src/partcad/plugin_request_provider_order.py#L14)), and `pc supply order` is four TODOs ([order.py:21-24](../src/partcad_cli/click/commands/supply/order.py#L21)). So whichever plugin ships first will, for a while, only quote. The third test therefore matters more than it first appears: a credential that can spend money sits in a plaintext file and travels with every command long before PartCAD can use its spending power.

**Craftcloud passes all three.** Its help centre lists STEP, 3MF and twelve more formats for 3D printing, in an article modified on 2026-10-27 ([Craftcloud formats](https://support.craftcloud3d.com/en/articles/189-which-file-formats-does-craftcloud-support-for-3d-printing-cnc-machining-sheet-metal-fabrication-and-molding-and-how-do-i-convert-them)). Its spec declares no security scheme for quoting or ordering ([Craftcloud spec](https://api.craftcloud3d.com/api-docs.json)). Its material catalogue is now known to be public: an unauthenticated 3.5 MB JSON lists 377 materials, 3,874 material configurations and 177 provider IDs, with `max-age=43200` ([Craftcloud material catalogue](https://customer-api.craftcloud3d.com/material-catalog?locale=en)). **3DAPI passes all three as well, behind a human gate.** It quotes STEP ([3DAPI file requirements](https://public-api.dapi.digital/docs/guides/file-requirements.md)). Its keys carry scopes in which `POST /v2/quotes` needs only `quotes:write` and placing an order needs `orders:write` ([3DAPI authentication](https://public-api.dapi.digital/docs/guides/authentication.md)). But approval takes a 24–48 h review of 10 sample files ([3DAPI approval](https://public-api.dapi.digital/docs/guides/request-integrator-approval.md)). **Slant 3D fails the first and third tests.** Its file type enum is `["stl"]`, and `POST /orders/{publicId}` will "begin production and charge payment" with the same unscoped key that reads the filament list ([Slant OpenAPI](https://slant3dapi.com/v2/api/openapi.json)).

And no rate limit is published. Craftcloud is still first because nothing in its flow puts a credential or a card in PartCAD's hands.

## Each provider's credential, mapped onto `pc login` and the three calls

In PartCAD a plugin credential is just a plugin parameter whose value the user has overridden. `pc login` asks the daemon to run the plugin's `login` api. The plugin calls `partcad_login.open_browser` with one capture per value: `cookie`, `localStorage`, `sessionStorage`, `dom`, `redirect` or `ask` ([plugin_login.py](../src/partcad/wrappers/plugin_login.py#L43); [login.rst](../docs/source/plugins/login.rst#L77)). A headless user or an agent answers the same call with `pc login --set name=value`, which in `--agent` mode is printed as instructions with exit status 3 ([login.py](../src/partcad_cli/click/commands/login.py#L144)). The **client**, never the daemon, then writes the value into `parameters:` of `~/.partcad/config.yaml`, at mode 0600 under a file lock ([user_config.py:1703](../src/partcad_utils/user_config.py#L1703)). From then on every command sends the client's whole resolved configuration with `context.create` ([service.py](../src/partcad_cli/click/service.py#L61)). The daemon folds each override into the declared parameter's `default`, and the plugin receives it in `request["parameters"]` on stdin, whatever sandbox it runs in ([plugin_factory_python.py:217-222](../src/partcad/plugin_factory_python.py#L217)). Three consequences follow. A credential must be **declared** in the provider's `partcad.yaml`, with a `default` such as `""`, or it never arrives. It must be a scalar ([plugin.py:151](../src/partcad/plugin.py#L151)). And it must be **long-lived**. Only `login` can return parameters, and only `pc login` or the MCP `login` tool saves them. A plugin that refreshes a token during `quote` has nowhere to put the new one. Any write to `config.yaml` would restart the daemon, because it watches the file's content hash every second ([config_restart.py](../src/partcad_service_json_rpc/config_restart.py#L6)).

The pattern that works within those limits is the one the incubated distributor plugins already use. The long-lived secret goes in `parameters`. The short-lived access token derived from it is cached by the plugin, at mode 0600, keyed by a digest of the secret ([distributor.py `bearer()`](../incubator/_shared/distributor.py#L937)). Every recommended provider fits it.

Geography follows from the same documents. Craftcloud prices in nine currencies, USD, EUR and GBP among them, with VAT-inclusive shipping lines per vendor ([spec](https://api.craftcloud3d.com/api-docs.json)). 3DAPI ships worldwide except Russia, Belarus, Iran and Syria, and EU and UK businesses pay VAT on wallet top-ups ([3DAPI FAQ](https://public-api.dapi.digital/docs/guides/faq.md)). Craftcloud has an `isTestOrder` flag whose effect on Stripe is undocumented, and 3DAPI says plainly "Every request works on your real account" ([3DAPI FAQ](https://public-api.dapi.digital/docs/guides/faq.md)). So every plugin is tested against recorded responses or mocks generated from the spec.

## A session cookie is the whole account, so the index should refuse it

Once captured, **PartCAD treats an API key and a session cookie identically.** Both become a string in `parameters:`, stored in plaintext in a 0600 file, sent with every `context.create`, and sent by the plugin as a header. Every difference lies in how the credential is obtained, how long it lives, what it can do, and who tolerates it. A key is pasted once from a developer page through an `ask` capture or `--set`, lasts until it is revoked, and is sometimes scoped. A cookie is read silently from PartCAD's own browser profile, HttpOnly included ([browsers/README.md](../browsers/README.md#L64)). It needs a `match` pattern or a `done_when.fetch` check so that a visitor's cookie is not mistaken for a signed-in user's ([login.rst](../docs/source/plugins/login.rst#L94)), and it carries the whole web account. PartCAD's existing cookie plugins (GrabCAD, Printables, MakerWorld) only ever *read*, and their worst case is a failed download. A print bureau's session also reaches the address book, order history, stored cards and the order button. SendCutSend's app vaults cards through Braintree, and Treatstock's upload page loads Braintree too ([SendCutSend app](https://app.sendcutsend.com/customer); [Treatstock upload](https://www.treatstock.com/upload)).

Today PartCAD's handling makes that blast radius worse, not smaller. **`pc config`, `pc system status config` and the daemon's status-config answer print every saved plugin credential verbatim.** This was confirmed on 2026-11-22 by running `config_report.resolved_options` against a temporary home directory holding a GrabCAD session: the output contained `parameter_config: ParametersConfig({'//pub/collection/grabcad:grabcad_repo': {'session': 'SECRETCOOKIE123'}})`. `option_value` redacts only `remote_sandbox_token`, `location`, `git_auth` and the `user` section ([config_report.py:39-128](../src/partcad_utils/config_report.py#L39)). The three commands print the result as it comes ([config.py:21-22](../src/partcad_cli/click/commands/config.py#L21); [status/config.py:41](../src/partcad_cli/click/commands/system/status/config.py#L41); [operations.py:2505-2506](../src/partcad_service_json_rpc/core/operations.py#L2505)). An agent can read the same answer through the MCP server, which lists `daemon.status.config` as context-free and does not refuse it ([server.py](../src/partcad_client/mcp_server/server.py#L54)). The module's own comment calls these outputs what people paste into bug reports ([config_report.py](../src/partcad_utils/config_report.py#L30)). Further from the machine, the whole `parameters:` section, every plugin's secrets, travels with every command whatever the command needs. The optional HTTP JSON-RPC transport has "no authentication yet" ([http.py](../src/partcad_service_json_rpc/transport/http.py#L10)), and the `remote` sandbox's client defaults to `http` ([remote_sandbox.py](../src/partcad/remote_sandbox.py#L384)). With a local daemon this is local IPC. With the remote daemon the code anticipates, it would be cleartext.

| Axis | Service-issued key or OAuth client | Captured web session |
| --- | --- | --- |
| Scope | Sometimes narrow: 3DAPI `quotes:*` without `orders:write` | Everything the account can do, stored cards included |
| Lifetime | Until revoked | Minutes to a browser session; Cloudflare's `__cf_bm` expires after 30 minutes of inactivity ([Cloudflare cookies](https://developers.cloudflare.com/fundamentals/reference/policies-compliances/cloudflare-cookies/)); PartCAD cannot write a renewed one back |
| Bot protection | API hosts answered datacenter clients (Craftcloud's API at 200 while its web front returned a Cloudflare challenge) | Xometry's homepage answered 429 with `x-datadome: protected`; Cloudflare's clearance cookie is "tied to the specific visitor and device it was issued to, preventing reuse across machines" ([Cloudflare clearance](https://developers.cloudflare.com/cloudflare-challenges/concepts/clearance/)) |
| Remote daemon or container | Works anywhere the parameter reaches | Replayed from another IP and TLS fingerprint; PartCAD's plugins identify themselves honestly and never answer a challenge ([plugin_models.py](../src/partcad/wrappers/plugin_models.py#L324)) |
| Two-factor sign-in | Passed once, when the key is issued | Every re-login needs a person, so agent and CI use breaks when the cookie expires |
| Revocation | Delete one key | Log out the session, or every session, without knowing a copy exists elsewhere |
| Terms | The sanctioned channel | Xometry §7.1.2 forbids "any manual or automated software devices"; §7.1.1 forbids reverse engineering its pricing algorithms ([Xometry agreement](https://www.xometry.com/service-agreement/)); Fictiv, Protolabs, Hubs and Treatstock forbid automation too ([Fictiv terms](https://www.fictiv.com/terms); [Protolabs conditions](https://www.protolabs.com/legal-notices/?tab=conditions-of-use)) |

The legal picture adds to the case against cookie replay rather than against API keys. In the US, a user reaching their own account is unlikely to breach the Computer Fraud and Abuse Act on a breach of terms alone. But *Facebook v. Power Ventures* held a third-party tool using users' own credentials liable once it kept going after a cease-and-desist letter ([Fenwick](https://www.fenwick.com/insights/publications/the-ninth-circuit-holds-that-accessing-a-website-after-receiving-a-cease-desist-letter-is-a-violation-of-the-computer-fraud-and-abuse-act)). *hiQ v. LinkedIn* ended in an enforced anti-scraping contract, a $500,000 judgment and an injunction ([Proskauer](https://newmedialaw.proskauer.com/2022/12/08/hiq-and-linkedin-reach-proposed-settlement-in-landmark-scraping-case/)). In the EU, *Ryanair v PR Aviation* lets a site enforce anti-scraping terms by contract ([Pinsent Masons](https://www.pinsentmasons.com/out-law/news/website-operators-can-prohibit-screen-scraping-of-unprotected-data-via-terms-and-conditions-says-eu-court-in-ryanair-case)). Providers pursue the intermediary as well as the user. Bambu's April 2026 takedown of an OrcaSlicer fork is the 3D-printing example ([Tom's Hardware](https://www.tomshardware.com/3d-printing/developer-re-enables-3d-printer-features-that-bambu-lab-disabled-firm-promptly-threatens-legal-action-orcaslicer-bambulab-project-now-shuttered)), and Home Assistant's withdrawal of MyQ shows the maintenance cost of building on a private API ([Home Assistant](https://home-assistant.io/blog/2023/11/06/removal-of-myq-integration/)). This is a summary, not legal advice. The direction is consistent all the same: the more a plugin looks like an unsanctioned client acting as the user, the more it exposes the user's account and PartCAD's name.

The recommended policy for the public index is therefore firm:

| Rule for `manufacturer` plugins in the public index | Reason |
| --- | --- |
| Authenticate only with a credential the service issues for programmatic use (an API key, OAuth client credentials, a sanctioned OAuth grant), or with none | The only credentials that are revocable, often scopable, exempt from bot protection and permitted by the terms |
| Never store a web-session cookie or a browser-storage token for a service that takes money. A `cookie` capture is allowed only to mint a key through the service's own key endpoint, and the cookie is then discarded | A session reaches stored cards and orders; GrabCAD-style read-only cookies remain acceptable for `//pub/collection` |
| Recommend the narrowest scope the service offers, and say in `login`'s guide which scopes ordering would need | 3DAPI is the only candidate where this works today; it is the habit worth setting |
| Never handle card data. `order` returns a hosted-checkout URL, or charges a card on file only after an explicit confirmation | Keeps PartCAD out of payment and caps what a leaked parameter can do through PartCAD |
| Declare every credential parameter (with `default: ""`, and `secret: true` once that exists), and read it from `parameters`, never from environment variables alone | Environment variables do not reach a container sandbox ([plugin_models.py](../src/partcad/wrappers/plugin_models.py#L1038)) |
| Refuse session-replay plugins for Xometry, Protolabs, Hubs, Fictiv, SendCutSend, Weerg and the PCBWay and JLC web apps. Pursue partner or OAuth registration instead (SendCutSend's Fusion add-in already uses PKCE) ([SendCutSend module](https://raw.githubusercontent.com/evtrapper/Fusion360-SendcutSend-Manual-Module/main/README.md)) | Terms forbid it, DataDome and Cloudflare defeat it across machines, and a user's account is what gets banned |

A user can still write a session plugin for themselves outside the index. PartCAD should not ship, pin or recommend one. The safest form of the idea, an agent driving the user's own signed-in browser and stopping at the cart, as the JLC ordering skills do, keeps the credential inside the browser and needs no PartCAD plugin at all ([ee-skills-claude-pub](https://raw.githubusercontent.com/pedro-setera/ee-skills-claude-pub/main/README.md)).

## Only a Bambu-dialect file reaches a service unchanged

PartCAD can already write the route a filament printer follows. `pc cam` turns a part's `fff:` declaration into G-code through `//builtin/cam:gcode`'s `MACHINES["fff"]`, with walls, skins and infill, layer by layer ([cam_gcode.py:1057-1062](../src/partcad/builtin/cam/cam_gcode.py#L1057); [additive.md §9.1](../docs/design/additive.md#91-pc-cam-writes-a-printers-route)). The design lets a slicer package run an unmodified PrusaSlicer or CuraEngine in a container as the route's `implementation:`, but the roadmap still lists that step as **proposed** ([additive.md §11](../docs/design/additive.md#11-roadmap)). None of this reaches a bureau today, because the manufacturer loader sends the **design**, not the print, as STEP ([plugin_factory_provider_manufacturer.py](../src/partcad/plugin_factory_provider_manufacturer.py#L25)). Every mesh bureau then re-slices with its own settings.

The services split into three groups. **No large bureau or marketplace takes G-code or a sliced file.** Craftcloud's spec has no slicer-project input. Slant's file enum is STL. Xometry's upload list is all design formats. Treatstock accepts STL, PLY and 3MF ([Treatstock formats](https://www.treatstock.com/help/article/37-what-types-of-files-are-supported-for-3d-printing); [Xometry formats](https://www.xometry.com/resources/3d-printing/comparing-infill-options-for-fdm-1/)). The most a structured order can carry is coarse. Craftcloud offers per-vendor priced options `infill_40` to `infill_100` plus a 1,024-character note. Slant takes a specific manufacturer's filament and colour. X3D takes a numeric `layerHeight`, `infill` and `nozzleDiameter` for unsliced files ([Craftcloud spec](https://api.craftcloud3d.com/api-docs.json); [X3D OpenAPI](https://x3dstudios.com/openapi.json)). **No service has a structured field for walls, top or bottom layers, infill pattern or build orientation.** Two small, Bambu-only fleets go further, and they can because a fleet of one printer model has one machine profile to check a slice against.

| Route | What is printed as-is | Dialect and machine | Readback | What PartCAD must build |
| --- | --- | --- | --- | --- |
| **X3D Studios** (US) | A sliced plate: "prints exactly as exported"; layer height, infill, supports, orientation "are whatever you set" ([X3D file formats](https://x3dstudios.com/docs/file-formats)) | Bambu `.gcode.3mf` for H2S or P2S; "A file sliced for a different printer model is a hard failure at the farm" | Grams and hours taken from the file; no slice or measurement back | A `.gcode.3mf` for an H2S/P2S profile; a test of whether the API's bare `.gcode` path really prints (its web docs say the farm needs a plate 3MF) |
| **3DAPI** (US + EU) | The project, not the route: a Bambu Studio or Orca 3MF with print settings, within fixed P1S, 0.4 mm nozzle, 0.20 mm layer and supports-on-plate limits ([3DAPI file requirements](https://public-api.dapi.digital/docs/guides/file-requirements.md)) | Bambu/Orca project 3MF; P1S | `file.production_version`: "This is the file that gets printed, and the one `price` is for", `null` when printed as uploaded, fixed once `ready`, signed URL for 15 min ([3DAPI quotes](https://public-api.dapi.digital/docs/reference/quotes.md)) | A project-3MF writer mapping `fff:` to Orca keys; a reader that compares `production_version` with what was validated |
| Craftcloud, Slant, Shapeways, Xometry, JLC3DP | The mesh or STEP only; the service slices | — | Volume, dimensions; Slant reports its own estimated weight and print time | Nothing beyond advisory notes |

| **Moonraker / Klipper** | `POST /server/files/upload` with `print=true` ([Moonraker docs](https://moonraker.readthedocs.io/en/latest/external_api/file_manager/)) | Plain G-code; LAN; key optional | Metadata, status | Same |
| **PrusaLink** | `PUT /api/v1/files/{storage}/{path}` with `Print-After-Upload: ?1` ([PrusaLink spec](https://raw.githubusercontent.com/prusa3d/Prusa-Link-Web/master/spec/openapi.yaml)) | G-code or `.bgcode`; `M862.3`/`M862.1` model and nozzle checks ([Prusa G-code](https://help.prusa3d.com/article/prusa-firmware-specific-g-code-commands_112173)) | Status, job | Same, plus the check lines |

"The delivered print equals the validated print" needs more than unmodified bytes. Prusa firmware applies its own pressure advance and input shaping unless the G-code sets them with `M572` and `M593` ([Prusa pressure advance](https://help.prusa3d.com/article/pressure-advance_814986)). Klipper defaults to `printer.cfg` unless `SET_PRESSURE_ADVANCE` and `SET_INPUT_SHAPER` override it ([Klipper G-codes](https://www.klipper3d.org/G-Codes.html)). Bambu's start command carries `flow_cali` and `vibration_cali` flags ([OpenBambuAPI](https://github.com/Doridian/OpenBambuAPI/blob/main/mqtt.md)). Ejection farms inject detachment sequences by design ([FarmLoop](https://help.3d-farmers.com/integrations/processing-api/)). So a faithful job names its printer model, nozzle and filament, pins every compensation it relied on, and is judged on the body of the route, while the farm's start, end and ejection blocks are allowed to differ. **No service or farm was found that commits to all of that in writing.** X3D's reprint promise covers failures "on our machine" and says nothing about a bad customer slice ([Why X3D](https://x3dstudios.com/why-x3d)).

PartCAD's own route is also not yet a print job a printer will run on its own. Reading [cam_fff.py:293-320](../src/partcad/builtin/cam/cam_fff.py#L293) shows it emits `G21`, `G90`, `M83`, the moves, and the CNC program end `M30`. It sets no temperatures, does not home, writes no model or nozzle check, and the design itself says the route has "no supports, no bridges, no seams" ([additive.md §9.1](../docs/design/additive.md#91-pc-cam-writes-a-printers-route)). Its file extension is `.nc` ([builtin/cam/partcad.yaml](../src/partcad/builtin/cam/partcad.yaml)), which OctoPrint's upload refuses with 415. A dialect that can carry the route itself to a service does not exist yet either. The 3MF Toolpath extension 1.0.0 standardises only bead speed, width and height for deposition, and lib3mf 2.5.0 does not implement it ([spec_toolpath](https://raw.githubusercontent.com/3MFConsortium/spec_toolpath/master/3MF%20Toolpath%20Extension.md); [lib3mf](https://pypi.org/project/lib3mf/)).

**The route that delivers the validated print soonest is the user's own printer**, or a makerspace's, through OctoPrint, Moonraker or PrusaLink. Each needs one upload-and-start call and a status read. The building work is a printer profile wrapping PartCAD's route in heat-up, homing, check lines, pinned compensations and an end block, plus a sender. The sender belongs in `partcad_client`, beside `pc ide open`, because a printer on the user's network is "this machine's" business and a daemon may be remote. Its credentials (an OctoPrint key, a Moonraker key) should stay client-side rather than in `parameters:`. Using these hosts is communication with programs, not importing AGPL or GPL code. That route is limited by what PartCAD's own route can print without supports.

**For a paid service, the enabling piece is a Bambu-dialect `.gcode.3mf`.** It reaches X3D, Bambu printers through Bambu Connect or Fleet Hub, and Printago farms. The cheapest correct way to produce one is the proposed slicer package running an unmodified OrcaSlicer or Bambu Studio in a container. `orca-slicer --slice 0 --export-3mf` already writes the plate, and `slice_info.config` carries its weight ([additive.md §12.4](../docs/design/additive.md#124-slicers-and-their-licences)). PartCAD would then validate that route rather than its own. Writing the container natively, as the MIT `bambox` does, is the alternative, but `bambox`'s bundled profiles derive from AGPL slicer sources ([bambox](https://pypi.org/project/bambox/0.4.6/)). Europe has no X3D equivalent; none was found, including in a German-language search. There, the 3DAPI project route with `production_version` readback is the closest thing to "print exactly this, and tell me if you changed it". Whether `production_version` is a sliced 3MF or a project with settings written in is unverified.

## Four fixes gate the first provider; the rest gate credentials, orders and printing

The earlier plan put STL export first. Craftcloud's STEP support and the confirmed credential leak reorder that: the leak is a defect for the GrabCAD and Printables users of today, before any print service exists.

## Conclusion

The second round of research changed the question more than the answer. The choice is not mainly between bureaus. It is about which credentials PartCAD is willing to hold, given that it holds every credential the same way and, until the redaction fix lands, prints them. Seen that way, the providers rank themselves by how little they ask PartCAD to hold. Craftcloud asks for nothing. 3DAPI asks for a key that can be made unable to spend. Slant asks for a key that can spend on its first misuse. A captured session asks for the whole account, against the service's terms and its bot defences. A firm index policy now is cheaper than retracting a cookie plugin later, and it puts PartCAD on the side of the vendors' sanctioned channels, which are the ones least likely to break.

"Exactly the print you modelled" turns out to depend on machine identity, not file format. The only services that honour a customer's slice are single-model Bambu fleets, so the format that carries a validated print to a third party is Bambu's de facto `.gcode.3mf`, not an open standard. The 3MF Toolpath extension will not carry an FFF job soon. That argues for two things built in parallel: a client-side sender for the open printer hosts, which pays off at once for anyone with an OctoPrint, Klipper or Prusa printer, and a containerised Orca slicer package that turns PartCAD's validation into something X3D, Printago and Bambu's own sanctioned routes will accept. 3DAPI's `production_version` is the one external feature worth copying into PartCAD's provider contract: a quote that says which file will actually be printed is what lets "validated" mean anything once a part leaves the user's hands.
